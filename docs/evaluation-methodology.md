# 决策评测方法、指标口径与实验边界

本项目分别回答两个问题：模型在明确的条件决策题中如何行动，以及批量评测任务能否在重试、取消和进程故障后可靠执行。前者需要真实模型结果，后者可用免费 mock 验证。两种证据分别报告，不能互相代替。本轮执行验收与新实验的结果见 [本轮验证与模型实验](evaluation-results.md)，后端执行机制见 [架构说明](architecture.md)。

对外结果只使用本轮新任务的报告与原始响应。仓库既有示例文件保留用于追溯，旧玩家成绩和旧探针统计不作为本轮结果展示。下文公式用于说明当前评分器实现，不是个人独立研究成果声明。

## 1. 评测对象与证据分层

| 数据 / 执行入口 | 观察单位 | 可以支持的结论 | 不能支持的结论 |
|---|---|---|---|
| 当前 `probe-v2` 真实模型执行 | 固定场景的一次有效决策 | 在公开生成假设和单步目标下，与条件参考策略的一致程度 | 真实整局最优策略、整局胜率、普适推理能力 |
| 当前 `mock` 执行 / Docker smoke | 任务、case、attempt、持久化结果 | 预算、幂等、租约、恢复和结果完整性在当前环境中的行为 | 模型质量、模型推理速度、生产吞吐与线上收益 |

原有完整游戏是 Python CLI 的多 Agent 博弈入口；Java 平台当前调度的是单步条件探针，尚未调度整局游戏。单步探针每个 case 重新构造输入，不沿用其他 case 的对话或 Agent 反思记忆。worker 的 checkpoint 是执行进度，不是 Agent 的语义记忆。

`SUCCEEDED` 表示任务中的 case 都执行成功并产生合法决策，不表示模型动作都符合参考。例如，所有响应格式合法、所有决策都偏离参考时，任务仍可以是 `SUCCEEDED`，参考一致率为 0。

## 2. v2 的公开生成假设

`analysis.probe.SUITE_VERSION = "probe-v2"` 定义一个合成条件参考问题。下列假设进入模型实际收到的 prompt，不由评测者在模型回答后另行补充：

1. **张数外生固定**：本手宣称张数在发牌前由外部指定，独立于所有玩家的手牌，不由出牌者根据手牌决定。
2. **重新随机发牌**：扣除质疑者自己的手牌后，出牌者从未见牌中均匀获得 5 张；这次发牌与此前回合和双方枪膛状态独立。
3. **诚实优先策略**：出牌者只要有足够目标牌或 Joker，就全部诚实出牌；否则仍需出指定张数，并包含至少一张假牌。不主动选择诈唬。
4. **没有额外行为信号**：行为描写是固定脚本；之前回合、对手印象和语气不提供额外的手牌信息。
5. **仅优化单步目标**：选择一次“质疑 / 不质疑”，效用为此次“对手被淘汰概率减自己被淘汰概率”。不质疑的单步效用定义为 0，不考虑长期存活、后续回合或信息价值。

这不是实际采样一手对手牌再用隐藏真值给模型判对错。v2 对未见手牌的分布进行解析计算，得到在这些条件下的参考动作；重复调用改变模型输出采样，不改变同一场景的参考标签。

## 3. 参考策略如何计算

### 3.1 诈唬概率：超几何分布

牌堆有 20 张牌：6 张 Q、6 张 K、6 张 A 和 2 张 Joker。目标牌与 Joker 都是本轮合法牌。质疑者看得见自己的 5 张牌，看不见出牌者的手牌。

| 记号 | 含义 | 当前默认场景 |
|---|---|---|
| `N` | 扣除自己手牌后的未见牌总数 | `20 - 5 = 15` |
| `K` | 未见牌中的合法牌数 | `8 - 自己手中目标牌与 Joker 的数量` |
| `h` | 出牌者出牌前手牌数 | 5 |
| `k` | 外生固定的宣称张数 | 1、2 或 3 |
| `X` | 出牌者手牌中的合法牌数 | `Hypergeometric(N, K, h)` |

因对手有足够合法牌就诚实，诈唬恰好发生于 `X < k`。因此：

$$
p = P(\mathrm{bluff}) = P(X<k)
  = 1-\sum_{x=k}^{\min(h,K)}\frac{\binom{K}{x}\binom{N-K}{h-x}}{\binom{N}{h}}.
$$

不可行的组合按 0 计。代码使用 `math.comb` 计算组合数，没有用手牌蒙特卡洛估计参考概率；模型输出的重复采样误差与参考概率的计算是两回事。实现见 [`analysis/risk.py`](../analysis/risk.py) 的 `synthetic_bluff_probability`。

`forced_bluff_floor`、`ProbeCase.bluff_floor` 和 `rational` 是兼容旧接口保留的名称。新解释分别是“v2 条件下的精确诈唬概率”和“条件参考动作”，不能按旧名字外推为真实博弈的策略无关下界或普适理性判断。

### 3.2 质疑门槛：单步效用

每名玩家使用 6 仓左轮，内有一发随机实弹。已开 `g` 枪且仍存活，说明此前 `g` 个仓为空；在这个条件下，下一枪命中率为：

$$
r(g)=\frac{1}{6-g},\qquad g\in\{0,1,2,3,4,5\}.
$$

记 `r_actor` 是出牌者下一枪命中率，`r_self` 是质疑者下一枪命中率。质疑成功时出牌者开枪，失败时质疑者开枪：

$$
U(\mathrm{challenge})=p\,r_{actor}-(1-p)\,r_{self},\qquad U(\mathrm{pass})=0.
$$

于是参考门槛及动作是：

$$
p^*=\frac{r_{self}}{r_{self}+r_{actor}},\qquad
 a^*=\mathbb{1}[p\geq p^*].
$$

`p = p*` 时固定选择质疑，用于保证标签确定；这只是平局约定，此时两种动作的单步效用都为 0。`margin = p - p*` 表示距门槛的距离，适合区分接近边界的分歧与明显偏离参考的分歧。

### 3.3 一个参考动作随风险翻转的例子

牌面 `noQ_3` 中，自己持有 `K, A, K, Joker, A`，目标为 Q，对手必须出 3 张。未见牌共有 15 张，其中 7 张合法牌，因此 `P(X<3) = 0.573426573`。

当前场景固定出牌者已开枪 0 次，`r_actor=1/6`：

| 自己已开枪 | 自己下一枪命中率 | 质疑门槛 `p*` | `margin` | 参考动作 |
|---|---|---|---|---|
| 0 | `1/6` | 0.500000 | +0.073427 | 质疑 |
| 1 | `1/5` | 0.545455 | +0.027972 | 质疑 |
| 2 | `1/4` | 0.600000 | −0.026573 | 不质疑 |
| 5 | `1` | 0.857143 | −0.283716 | 不质疑 |

同一手牌、同一出牌张数的条件诈唬概率没有变；自己的错误质疑成本上升，使参考动作从 `gun1` 到 `gun2` 翻转。这一对比检验的是固定条件下对风险门槛的响应，不是两次实际游戏之间的因果对照。

## 4. 场景覆盖、类别分布与最简单基线

`make_cases()` 目前固定 8 个牌面，每个牌面遍历质疑者 0–5 枪，共 **48 个不同输入状态**。出牌者固定 `actor_gun=0`、出牌前手牌 5 张；所有默认目标均为 Q。若选择 `B` 个牌面、每个状态重复 `R` 次，一种规则文本的计划样本数为 `6 × B × R`。CLI 选择两种规则文本时再乘 2。

| 牌面 ID | 自己手牌 | 对手宣称张数 | 条件诈唬概率 | 参考质疑的自己枪数 |
|---|---|---|---|---|
| `noQ_1` | K, A, K, Joker, A | 1 | 0.018648 | 无 |
| `noQ_2` | K, A, K, Joker, A | 2 | 0.181818 | 无 |
| `noQ_3` | K, A, K, Joker, A | 3 | 0.573427 | 0、1 |
| `noQ_A2` | A, A, A, A, A | 2 | 0.100233 | 无 |
| `noQ_A3` | A, A, A, A, A | 3 | 0.426573 | 无 |
| `AJJ_2` | K, K, K, Joker, Joker | 2 | 0.293706 | 无 |
| `QQQ_2` | Q, Q, Q, Q, Q | 2 | 0.758242 | 0、1、2、3、4 |
| `QQJ_3` | Q, Q, Q, Joker, Joker | 3 | 0.978022 | 0、1、2、3、4、5 |

全量 48 个状态中，**13 个参考质疑，35 个参考不质疑**。因此：

- 永远不质疑的策略，在无失败且均匀覆盖这 48 个状态时已有 `35/48 = 72.9%` 参考一致率。
- 永远质疑的策略为 `13/48 = 27.1%`。
- 与参考无关的公平随机质疑策略，其期望参考一致率为 50%，有限次 mock 的实测值可偏离 50%。

这些数字是当前全量套件的基线；只选择部分牌面时必须重新计算类别分布。不能仅因总体一致率超过 50% 就声称模型有效，也不能把在高比例“不质疑”场景上的保守行为视作完整的风险响应能力。

当前 8 个牌面是手工选择的覆盖集，不是实际游戏状态的随机样本。默认集尚未覆盖出牌者 1–5 枪、不同手牌规模、不同目标牌、真实历史和不同对手策略。牌面间行为文本也不同，不能把跨牌面差异全部归因于手牌。扩展覆盖后需版本化套件并重新生成报告。

## 5. 样本、重复、seed 与文本对照

需要区分三个层级：`probeId` 是一个冻结状态；`repeatIndex` 是该状态的重复采样；Worker 的 `attempt` 是为了完成一次计划样本而进行的调用尝试。增加重试次数不是增加独立评测样本。

| 入口 | seed 规则 | 重复 / 重试语义 |
|---|---|---|
| `python -m analysis.probe` | `base_seed + repeatIndex`，不同状态复用对应重复的 seed | 一个计划样本只发一次新请求，SDK 自动重试关闭；可恢复身份完全匹配的成功日志 |
| Java + Python Worker | `run_seed + case ordinal`；展开顺序为请求中的 boards、gun 0–5、repeatIndex | 同一 case 重试复用该 case seed，每次新尝试先预留预算；成功后形成唯一 checkpoint |

两种入口的 seed 方案不同。即使 base seed 相同，也不能把二者当成相同请求或直接拼成配对实验。提供方是否支持 seed、是否会更新模型、并行请求是否影响确定性，都不由本地代码保证；`temperature=0` 也不是确定性承诺。

两套规则文本为 `threat` 与 `neutral`。中性版删除原规则首行的生存威胁措辞，其余规则保留。CLI `--rule-base both` 在相同场景、重复编号和请求参数下执行两种文本；它按固定顺序执行，尚未随机交错请求次序。若要解释为文本干预效果，应使用场景配对差值并控制时间、版本、顺序等因素，不能把两组总率的差异直接解释为因果效应。

共享 prompt 的多次调用只估计该 prompt 下的输出波动，不能把 `48 × R` 次响应说成 `48 × R` 个独立牌面。枪膛状态还共享同一个基础牌面，进一步推广时需要考虑牌面内相关。

## 6. 当前已实现的指标及分母

### 6.1 Java 聚合报告

`GET /api/runs/{id}/report` 的实际口径由 [`RunService.report`](../control-plane/src/main/java/io/github/liveoveryu/eval/RunService.java) 实现：

| 字段 | 实际口径 | 解读限制 |
|---|---|---|
| `totalCases` | 创建时计划的样本总数 | 包括尚未执行和最终失败的 case |
| `completedCases` | 已有成功或失败 checkpoint 的 case 数 | 完成不等于成功 |
| `successCases` / `failureCases` | 成功 / 最终失败 checkpoint 数 | 重试失败的 attempt 不一定导致 case 最终失败 |
| `challengeRate` | 成功 attempt 中 `wasChallenged=true` 的比例 | 失败响应不进入分母；无成功响应返回 `null` |
| `agreementWithReference` | 有参考标签的成功 attempt 中，动作等于参考的比例 | 这是有效响应条件下的一致率；失败不自动算“正确”或“错误”，无可比较结果返回 `null` |
| `callCount` | 持久化预留的 attempt 数 | 含重试及未回传的尝试，不等于已确认的供应商调用数 |
| `errorCounts` | 已回传 `ERROR` attempt 按错误类别计数 | 是尝试级次数，不能直接当成最终失败 case 数 |
| `p95LatencyMs` | 所有 `FINISHED` attempt 的 `latencyMs` 排序后，取第 `ceil(0.95*n)` 个 | 含成功与失败尝试，不是端到端任务延迟 |
| `totalTokens` | 已回传 attempt 的 prompt tokens 与 completion tokens 之和 | 包括有 usage 的失败调用；未知或缺失 usage 记入值可能为 0，不等于实际账单为 0 |
| `unfinishedAttempts` | 仍为 `STARTED` 的 attempt 数 | 暴露已预留但结果未知的尝试 |

当前成功会立即完成该 case，结果重放不重复计数，因此正常协议下每个成功 case 对应一个成功 attempt。`latencyMs` 是 Worker 单次 `evaluate` 计时，包含客户端构造、模型请求、解析、关闭及首次源码指纹计算，不含排队、预算预留 HTTP、退避和结果回传 HTTP。mock 延迟是本地模拟执行耗时，不能与真实模型推理速度混为一谈。

### 6.2 CLI 报告

CLI 的 `by_case` 只保存严格解析成功的布尔动作，其中可能包含本次新请求和恢复的缓存结果。`total_calls` 仅为本次新发出的请求数，`resumed_calls` 是复用次数；格式失败和 API 失败分别计数。正常完成时，有效响应数为 `total_calls - format_failures - api_failures + resumed_calls`。鉴权错误会提前终止，manifest 标记失败，不能把未执行样本默认为“不质疑”。

CLI 逐状态质疑率和参考一致性以有效响应为分母；没有有效样本的状态应显示“无样本”。内部 `_rate([])` 的数值占位 0 不能在图表中画成“模型 0% 质疑”。全部命中缓存时，可以有有效样本而 `total_calls=0`。

### 6.3 报告时必须同时给出的覆盖信息

比较两个模型时，应同时展示计划 case 数、成功 case 数、最终失败数、未完成数、预留调用数和错误分布。可以根据现有字段计算 `successCases/totalCases` 作为有效决策覆盖率，但当前 Java 报告没有单独命名这一派生指标。高一致率若只来自少数成功样本，不能说明整个任务质量高；重试更充分的配置也不能与仅调用一次的配置不加说明地排名。

示例：计划 100 个 case，只有 10 个成功且均符合参考，一致率可为 100%，覆盖率却只有 10%。两者必须一起报告。

## 7. 类别、场景与效用层面的补充指标

当前 Java API 已实现总体参考一致率，尚未直接返回下表中的模型质量指标。本轮绘图脚本已从新实验的导出结果离线计算参考正负类的命中与覆盖，以及以全部计划样本为分母的一致率；这不代表 Java API 已增加相应字段。其余指标可按下列定义继续补齐，展示时应注明实际实现的位置：

| 建议指标 | 定义 / 用途 |
|---|---|
| 参考质疑召回率 | 参考为质疑的有效样本中，模型选择质疑的比例，检查是否漏掉少数类 |
| 参考不质疑召回率 | 参考为不质疑的有效样本中，模型选择不质疑的比例 |
| Balanced accuracy | 上述两类召回率的平均；两类均有有效样本时才有完整定义，避免 72.9% 多数类基线掩盖问题 |
| 场景宏平均一致率 | 先对每个 `probeId` 算一致率，再在有有效响应的场景上等权平均；必须同时报告缺失场景与其参考类别 |
| margin 分层 | 按 `p-p*` 分桶，分别报告样本数、覆盖率与动作分布，观察门槛附近是否翻转 |
| 单步效用遗憾 | 每个有效动作的 `max(U(challenge),0) - U(所选动作)`，再按明确权重汇总；只适用于 v2 单步效用 |

在完整均衡重复、无缺失的实验中，样本微平均与按场景宏平均可以相同；失败或恢复导致有效重复数不同后，两种权重可能明显不同。缺失场景不能静默丢弃。

一致率把每次参考不一致都算一次，但动作在 `margin` 接近 0 时几乎无单步效用差；选反时的单步遗憾为 `abs(p-p*) × (r_self+r_actor)`。效用遗憾能区分这种差别，不过其单位仍是定义的“期望淘汰差”，不能换算成真实胜率或金钱收益。当前输出是离散动作，未要求模型提供可校准的诈唬概率，所以现有“校准表”是动作响应曲线，不是概率校准曲线，也不能直接计算概率 ECE / Brier score。

## 8. 不确定性、比较与统计限制

`analysis.stats.wilson` 给出二项比例的 Wilson 95% 区间。它在重复响应近似独立且概率稳定的前提下，表达有限次布尔采样的不确定性；把所有响应当独立同分布后计算的合并区间，不包含牌面选择、模型版本变化、供应商相关噪声等不确定性。已有 CLI margin 分桶区间是响应级描述，不能据此声称对真实游戏状态总体的置信度。

对真实完整游戏，局内决策共享发牌、对手和轨迹，应以游戏为簇进行重采样；`analysis.stats.cluster_bootstrap` 提供按簇 bootstrap 工具，但不能因此宣称所有已有统计都已做聚类修正。对多次同场景探针，可先报告逐状态重复分布；推广到更多状态时，可按基础牌面保留内部结构重采样，并明确只有 8 个牌面，区间本身也不稳定。模型 / 文本比较宜使用相同场景与重复编号的配对差值，并保留失败、版本和采样参数。

图表中的区间必须标清方法、统计单位与分母。未处理局内或牌面内相关时，不给出泛化的显著性结论；没有足够独立单位时，先展示样本量和逐场景分布。有限次置换或 bootstrap 也不能把数值占位当作确定性证明。

## 9. 失败、重试与未知消耗

CLI 探针每个计划样本一次请求，SDK 自动重试关闭；格式错误和 API 错误单独计数，鉴权错误快速失败。完整游戏的普通玩家输出修复路径可尝试至多 5 次，每次失败都有计数，网络或鉴权错误直接传播；该路径不等于平台评测的重试协议。

Worker 将重试显式交给任务系统，每次调用前先预留 attempt。`maxAttempts` 限制一个 case，`maxCalls` 限制整个 run，`timeoutSeconds` 与 `maxOutputTokens` 限制单次请求。重试成功是“最终得到合法决策”，不会因模型动作不符合参考而继续重试，以免挑选答案。

| 类别 | 当前行为 |
|---|---|
| `FORMAT` | 严格 JSON / 字段类型或动作契约不合法，在预算内可重试 |
| `RATE_LIMIT`、`TIMEOUT`、`NETWORK` | 在预算内按有上限的指数退避重试 |
| `AUTH` | 不重试；记录后停止本次 run，避免继续调用后续 case |
| `PROVIDER` | HTTP 5xx 可重试，其他供应商 HTTP 参数等错误不可重试 |
| `INTERNAL` | 不自动重试，记录本地执行失败 |

失败不可重试、达到 case 尝试上限或达到全局预算时，形成失败 checkpoint；全局预算可能在后续 case 尚未执行时耗尽。恢复保留预算与所有 checkpoint，跳过已完成的成功和失败样本；要重新评测已失败样本应创建新任务，不能清零旧计数。

预留后崩溃可能发生在供应商调用前，也可能发生在模型回答后、回传落库前。控制面不能知道外部是否执行或计费，因此该 attempt 仍占预算，并由 `unfinishedAttempts` 显示未知状态。它保证有界调用和本地幂等计数，不保证供应商请求 exactly-once。`totalTokens=0` 尤其不能消除未知消耗。当前实现的是调用次数预算，尚无按供应商价格表执行的货币硬预算或统一 QPS / TPM 限流。

## 10. 条件参考的适用范围

真实游戏里，出牌张数由对手根据手牌和历史选择。观察到“出 3 张”后，需要计算动作条件下的手牌后验；随机发牌的边际概率不能直接作为诈唬概率。

反例：自己持有 3 张 Q 和 2 张 Joker，未见牌里只有 3 张 Q。随机抽 5 张凑不齐 3 张 Q 的概率约为 0.978。但若对手的策略是“拿齐 3 张 Q 才出 3 张，否则出 1 张”，观察到出 3 张后，诈唬概率可以为 0。因此 0.978 不是任意策略下的诈唬率下界。

当前评分器用公开的“外生张数 + 诚实优先”假设定义条件参考动作。这缩小了结论范围：只判断模型是否遵循这组明确假设，不能将单步一致率换算成自由博弈胜率，也不能给缺少这些假设的旧记录重新判分。

不质疑的即时效用记为 0；如果改变一次质疑会结束小局并改变后续轨迹，便需要重新运行整局实验。当前平台没有调度整局反事实重放。已有原始数据不修改，旧结果不纳入当前实验成绩。

## 11. 状态合法性、动作校验与可追溯性

合成状态的回合编号至少为 `1 + actor_gun + challenger_gun`，旁观者枪数为 0，实弹放在未开过的位置，避免“第 1 轮已开 5 枪”或历史已经中弹却仍存活的矛盾。这是让单个冻结状态自洽，不代表重建了一条真实完整游戏轨迹。

质疑动作通过 `parse_action` 校验严格 JSON、布尔值与理由字段类型。完整游戏出牌还通过 `Counter` 校验重复牌数量；全部校验成功后才提交剩余手牌。格式或网络失败不消耗手牌，不能用“每张牌都在手牌中”替代多重集库存检查，也不对布尔值、列表和理由做隐式类型转换。

CLI 每次运行默认创建唯一目录，包含 `manifest.json`、`probe.json` 和有请求时生成的 `raw.jsonl`。manifest 保存套件版本、模型请求名、温度、seed、规则文本条件、prompt SHA-256 与输出位置。恢复使用新目录和 `--log <旧 raw.jsonl>`，只复用 suite、prompt/hash、模型、温度、seed、重复编号完全匹配且动作合法的记录；损坏尾行忽略，旧 v1 日志不自动复用。

Worker 逐 attempt 回传原始 prompt / 响应、prompt hash、模型版本、供应商 request ID、延迟、usage、错误类别和源码指纹。当前会检查套件版本和 prompt 哈希一致性，尚未强制一个 run 只能由相同源码指纹的 Worker 执行。实验应固定 Worker 版本；源码或供应商模型变化时创建新实验，评测语义变化时提升 suite 版本。记录指纹提供核验线索，不等于强制版本隔离。

## 12. 免费复现与真实模型实验

以下命令不调用模型 API。先在仓库根目录安装依赖并准备 Java 环境，详细启动步骤见 [README](../README.md)：

```powershell
# 查看实际 prompt、48 个场景和参考标签，不创建模型请求
.\.venv\Scripts\python.exe -m analysis.probe --dry-run --rule-base both --repeats 5

# Java / Python 回归与故障注入
mvn -f control-plane/pom.xml verify
.\.venv\Scripts\python.exe -m unittest discover -s tests -v

# 已启动 Compose 后，用 mock 验证任务链路
.\.venv\Scripts\python.exe scripts/smoke_compose.py
```

`dry-run` 下两种文本、48 个状态各重复 5 次对应 480 次计划调用，但不会真正发送。Docker mock 的 72 个成功样本和预算失败任务是执行系统验收，不计入真实模型质量样本，详见 [Docker 验收记录](docker-verification.md)。本轮新实验的配置、分子分母与来源文件在 [本轮验证与模型实验](evaluation-results.md) 记录，未核验完成前不公布分数。

真实模型实验应先固定 suite 与源码版本、完整场景和规则、模型与请求参数、seed 方案、预算及重试策略，再分别记录覆盖率、总体一致率和分类表现。每个模型使用相同计划条件；保留失败、原始响应和全部尝试，报告真实数据而非 mock。一旦要评价长期策略，就必须另设完整游戏实验，固定对手组合、种子和座位轮换，不能把单步分数直接改名为整局胜率。
